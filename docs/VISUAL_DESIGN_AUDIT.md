# 《BuildRogue》视觉与 UI 设计审计

> 阶段：Pre-production / Vertical Slice
>  
> 审计日期：2026-08-16
>  
> 设计依据：当前 Godot 4.6 项目的 scenes、scripts、data、UI 与现有 art 资源。

## 1. Executive Summary

当前项目的玩法骨架已经足以支持一次有针对性的视觉重构：共有 33 件法宝、5 个体系、7 个属性，包含双属性、1–3 星、5 档品阶、出战区/储物袋、刷新与锁定、修为突破、聚灵、天命和奇遇。视觉层仍处于“功能原型”阶段，最大问题不是不够华丽，而是缺少一套让玩家在 1–2 秒内完成构筑判断的统一编码。

推荐采用方向 A「云笺百宝」：Q 版国风剪影、扁平手绘、宣纸与印章语汇、现代 Roguelite 信息架构。它能保留轻松修仙感，同时把法宝轮廓、属性符号和危险预警放在装饰之前，适合大量敌人同屏，也适合用 Godot 的 Sprite2D、Polygon2D、Line2D、Theme 与少量 Tween 实现。

本阶段不建议直接替换运行时 UI。原因是 `scripts/game_ui.gd`、法宝数据和相关测试已有未提交修改，且本机未发现可运行的 Godot 编辑器/二进制，无法完成可靠的视觉回归。应先确认本文件的方向，再按 `ART_BIBLE.md` 制作一个可运行的 Vertical Slice。

## 2. 项目事实与核心信息

### 2.1 当前技术与画面基线

- 引擎：Godot 4.6，2D 场景使用 Forward Plus。
- 主流程：主菜单 → 初始法宝 → 60 秒战斗房间 → 商店/突破 → 天命/奇遇 → 结算。
- 世界尺寸：竞技场 `1120 × 672`；玩家 Camera2D 缩放为 `1.2`。
- `project.godot` 未显式声明窗口逻辑分辨率、stretch mode、aspect policy 或 UI 缩放策略；当前实际显示行为依赖引擎/运行环境默认值。
- 当前场景背景是深蓝灰矩形、100 单位网格、简单树石 Polygon2D。
- 玩家显示尺寸约 `32 × 48` 世界单位；两个已有敌人图片以 512 图源缩放到约 38–44 世界单位，其余敌人仍是彩色几何占位。
- 当前贴图导入未生成 mipmap；像素/手绘混合资产没有一套显式的过滤规则。

### 2.2 玩家最重要的信息

战斗中：

1. 自己的位置、生命与护盾。
2. 立即危险：冲锋线、敌方弹体、Boss 范围、接触包围。
3. 房间剩余时间与波次/Boss 状态。
4. 当前法宝是否在工作、攻击节奏是否正常。
5. 构筑已激活的关键羁绊和临时状态；不是完整羁绊百科。

商店中：

1. 这是什么法宝，战场上长什么样。
2. 攻击形态与主要机制。
3. 体系、主/副属性，以及购买后会推动哪条羁绊。
4. 星级、品阶、价格与是否买得起。
5. 与当前持有同名法宝的合成/升星关系。
6. 出战区容量、储物袋容量、出售和移动结果。
7. 修为是否已满、突破缺什么、刷新/聚灵的机会成本。

## 3. 当前视觉与 UI 问题

### P0 — 会影响可玩性或验证的结构问题

1. **缺少明确的显示基线。** 没有逻辑分辨率、stretch、safe zone 和 UI scale，意味着同一套固定 offset 在 720p、4K、超宽屏上会出现不同问题。
2. **控制器导航基本不可用。** 商店卡、锁定、刷新、突破、聚灵、天命与奇遇卡片都设置了 `FOCUS_NONE`。鼠标可完成流程，但手柄/键盘焦点无法完成核心构筑循环。
3. **关键状态未可视化。** `set_shield()` 为空；战斗 HUD 只用文本显示生命，缺少生命条、护盾层、受伤方向/低血量冗余编码。
4. **UI 安全区不足。** HUD 左上固定为 12 px，底栏距底 12 px，没有 5% title-safe 容器；电视 overscan 或 UI scale 增大时会被裁切。

### P1 — 直接影响战斗与构筑读取

1. **字号过小。** 战斗法宝名/星级为 11，羁绊正文 12、标题 13，商店标签 13，储物袋标签甚至 10。动态背景和 10-foot/Steam Deck 场景下不可接受。
2. **羁绊是长文本清单，不是状态仪表。** 战斗 HUD 同时显示全部 12 个体系/属性条目以及天命/奇遇，既遮挡战场，又让“已激活/差 1 个/无关”无法一眼区分。
3. **颜色承担了过多含义。** 羁绊激活层级和品阶主要靠颜色；没有稳定的形状、节点数、角标或线框层级作为色觉冗余。
4. **商店层级平均化。** 卡片同时展示图标、名字、星级、标签、短描述、价格，但缺少“购买会达成羁绊”“可合成”“买不起”“已锁定”等决策强提示。
5. **Tooltip 使用系统默认路径。** 商店和多数库存依赖 `tooltip_text`，出现时机、位置、宽度和对比度不可控；战斗法宝 Tooltip 自建但 hover 延迟只有 0.08 秒，容易闪烁。
6. **法宝 Icon 与 World Sprite 脱节。** 现有 icon 是深色圆角方卡中的扁平图形；战场效果由 Line2D/Polygon2D 临时绘制，核心轮廓与比例经常不同，玩家无法建立稳定识别。
7. **图标覆盖不完整且存在复用错义。** 33 件法宝中 6 件召唤法宝没有 icon；神雷术复用天眼、火葫芦复用法球、巨剑术复用飞剑、吼复用衣袍、镰刀复用血剑、招魂幡复用毒针等。
8. **同屏颜色没有阵营预算。** 玩家技能、敌人类型、品阶、羁绊、属性都在争夺高饱和色。敌方远程目前为青色、冲锋为橙色，而玩家水/雷/火也使用相近颜色，危险归属容易混淆。

### P2 — 一致性、品质与生产问题

1. **画风混用。** 玩家是高细节 AI 像素/Q 版立绘风，敌人是低色数像素块，其他敌人是纯几何；图标又是平滑矢量式扁平设计。
2. **视角不一致。** 玩家是侧面全身，敌人接近侧面/图标视图，竞技场为俯视；移动方向和受击朝向缺少共同规则。
3. **敌人类型主要靠颜色。** Tank、Ranged、Charger、Boss 的占位几何虽有形状差异，但还没有统一的头身比、朝向、命中体积与阴影标准。
4. **伤害数字缺少描边/底衬。** 当前仅改变 modulate 色，在火球、雷电或浅背景上会丢失；连续伤害也可能形成数字雨。
5. **卡片与面板过度依赖代码内联样式。** 颜色、圆角、间距散落于脚本，后续难以建立 Theme token、色盲模式、UI scale 和批量改版。
6. **主菜单、天命、奇遇、结算只是功能容器。** 没有统一的世界观框架、页面转场、输入图例和返回路径；当前没有设置页。

## 4. 值得保留的内容

- HUD 的基础锚点是合理的：资源左上、波次/时间上中、法宝栏下中；中心战斗区保持空白。
- 商店采用“商品区 + 出战区 + 储物袋 + 右侧羁绊”的大结构，符合构筑逻辑，应重排而非推翻。
- 卡片已有图标、名称、星级、体系/属性、描述、价格和锁定信息，数据接口足够支持渐进式信息披露。
- `ArtifactData` 已提供 attack template、attack shape、effect type、主副属性、品阶、价格、升星与特殊机制字段，可直接驱动视觉标签。
- 法宝战场效果采用程序几何，制作成本低，且很适合将轮廓统一后继续复用。
- 伤害数字与 hit effect 已对象池化；同屏大量敌人的性能方向正确。
- 敌人已有基础、快速、坦克、远程、冲锋、Boss 的清晰行为分类，适合做“轮廓即行为”的敌人设计。

## 5. 三套视觉方向

### Direction A — 云笺百宝（推荐）

**核心关键词：** Q 版修仙、扁平手绘、剪影清晰、宣纸、墨线、朱印、轻喜剧、现代构筑 UI。

**UI 风格：** 深墨蓝半透明底板 + 暖宣纸内容面；边框像一笔压下的墨线，不做金色雕花。体系使用印章形徽记，属性使用几何符号，品阶使用边框结构。商店像“百宝摊”的现代仪表板，而不是古代卷轴。

**人物风格：** 2.5 头身、俯视 3/4、宽袖与高马尾形成核心轮廓；32×40 或 40×48 的世界显示尺寸。只做 1 个主朝向 + 水平翻转，移动采用 2–4 帧或程序 bob/倾斜。

**敌人风格：** 水墨纸偶与妖怪剪影；行为优先于服饰细节。基础敌人圆/窄，坦克方/宽，远程上宽下窄，冲锋箭头形，Boss 使用双层轮廓。

**法宝风格：** 每件法宝先定义一个 24–40 px 仍可辨认的黑色核心轮廓；UI icon 与 World Sprite 共用该轮廓，UI 只增加纸卡底、属性角印和一处高光。

**场景风格：** 低饱和青灰石坪、宣纸纤维和稀疏墨迹；场景物件只使用 3 个明度层，不抢属性色。

**特效风格：** 一次攻击最多“轮廓实体 + 属性色 + 一层墨迹/符纹”。火是朱砂楔形，水是青蓝波纹，雷是断折白蓝线，毒是紫绿点簇。

**优点：** 主题鲜明但不妨碍信息；Icon/World 统一最自然；程序图形可直接风格化；对同屏数量友好；方便逐件扩产。

**缺点：** 需要严格控制纸纹和墨线，做差会显得像普通扁平 UI；角色画面冲击力不靠高细节。

**生产成本：** 中低。核心工作是轮廓设计、统一色板和 Theme；动画成本低。

**Godot 2D 难度：** 低到中。Sprite2D、NinePatchRect/StyleBoxTexture、Line2D、Polygon2D、Tween 足够。

**大量敌人同屏：** 很适合。粗轮廓、小色面、低纹理频率能保持聚类可读性。

### Direction B — 灵境剪纸

**核心关键词：** 高饱和剪纸、民俗玩具、夸张几何、喜剧、强轮廓、印刷错位。

**UI 风格：** 米白底、黑红主界面、大块拼贴标签；按钮像纸片压在木板上，选择时产生 2–3 px “套色错位”。

**人物风格：** 2 头身纸片人，四肢与武器极度概括；可以只做静态 body 加局部旋转。

**敌人风格：** 每类敌人由一个基本几何决定：圆、方、三角、菱形；脸谱只保留两个标记点。

**法宝风格：** 类似印章/木版画的单色剪影，战场 Sprite 像飞出的纸符与木刻图样。

**场景风格：** 层叠纸张、云朵和山形，阴影像纸片离底 2–4 px。

**特效风格：** 爆炸使用星芒纸片，斩击用撕纸裂口，状态用盖章；基本不用透明辉光。

**优点：** 辨识度最高；最低动画成本；轮廓在混战中非常稳定；适合轻松搞笑。

**缺点：** “修仙”会更接近民俗/童玩；长线内容若只靠几何，仙宝的成长感较难拉开；部分玩家可能觉得过于休闲。

**生产成本：** 低。

**Godot 2D 难度：** 低。

**大量敌人同屏：** 最适合，但需要降低饱和背景，避免全屏像彩纸屑。

### Direction C — 青瓷霓符

**核心关键词：** 青瓷、夜色、玉石、阵法 HUD、冷色灵光、现代战术、克制神秘。

**UI 风格：** 深青黑底、薄玉片、白色信息线；符箓只作为角标和进度节点。商店像修士的灵识阵盘，信息密度高且精确。

**人物风格：** 3 头身简化剪影，衣边有单条灵力色；细节比 A 更冷峻。

**敌人风格：** 深墨实体 + 一处危险器官/符核；威胁通过高亮弱点和预警线表达。

**法宝风格：** 深色实体、玉质边缘、单色能量核心；Icon 以切面和材质区分。

**场景风格：** 夜间山门、青石与薄雾，背景很暗；阵纹只在事件时短暂出现。

**特效风格：** 细线符阵、能量扫光、少量 additive glow；强调攻击前摇和精密轨迹。

**优点：** 战斗对比度好；高级感强；现代 UI 与构筑深度匹配；仙宝成长容易做。

**缺点：** 容易滑向“所有东西都发光”；轻松有趣感较弱；暗背景上的敌人轮廓需要额外描边；同屏特效预算更难管。

**生产成本：** 中高。

**Godot 2D 难度：** 中。需要更多 CanvasItemMaterial、遮罩、发光与过绘控制。

**大量敌人同屏：** 条件适合；必须实行严格的 glow 数量上限和敌我色域分离。

## 6. 推荐结论

选择 **Direction A「云笺百宝」**。

它最符合项目的真实矛盾：玩法数据很多、同屏对象很多、资源预算有限，但法宝必须有收藏感和身份。A 能用“共同核心轮廓”解决 Icon/World Sprite 断裂，用“纸、墨、印章”建立修仙世界观，又不会像传统仙侠手游那样依赖金框、卷轴和泛光。它也允许后续在 Boss、仙宝和突破界面局部借用 C 的青瓷/灵光质感，而不破坏基础系统。

不采用纯像素美术作为最终方向。当前资产源尺寸、缩放比例和 UI 图标并未形成像素网格一致性；若强行走像素路线，需要重做所有人物、敌人、Icon 与导入规则，成本反而更高。

## 7. Vertical Slice 方案

### 7.1 目标

用一个可运行战斗房间验证以下假设：

- 玩家在 1 秒内能定位自身和三类威胁。
- 6 件法宝在商店 icon、底栏 icon 和战场表现之间能互相认出。
- 属性颜色在 30+ 敌人、5+ 技能同时存在时仍不混淆阵营。
- 玩家能在 3 秒内判断一张卡是否买得起、是否能升星、是否让羁绊达标。
- 鼠标、键盘与手柄均能完成“锁定 → 刷新 → 购买 → 移动 → 出售 → 继续”。

### 7.2 样板内容

**玩家：云游小修士**

- 2.5 头身，俯视 3/4，黑发高马尾、米白内衫、墨青短袍、朱红腰印。
- 32×44 世界显示尺寸，轮廓外扩 1.5–2 px，脚下 18×7 半透明墨影。
- 移动只用 4 帧循环或程序 bob + 轻微朝向倾斜；左右翻转，不做八方向。

**敌人：**

1. 纸傀邪修（Basic）：窄长人形、黄符手臂，群体压力基准。
2. 符弩散修（Ranged）：菱形斗笠 + 横向弩臂，前摇时符核变为敌方警示纹。
3. 赤角冲阵妖（Charger）：前宽后窄箭头轮廓，冲锋线有危险三角与倒计时收束。

**6 件法宝：**

| 法宝 | 当前模板 | 角色 | 属性 | 样板验证点 |
|---|---|---|---|---|
| 长枪 | melee | 近战 | 火 | 实体枪尖与火色突刺必须一致 |
| 巨剑术 | projectile | 发射物 | 金 + 土 | 大轮廓、双属性角标、重击反馈 |
| 护体剑轮 | orbit | 环绕 | 木 | 多实体不形成视觉花圈 |
| 神雷术 | target_aoe | 范围 | 雷 | 敌我预警、前摇与命中分层 |
| 幽魂 | summon | 召唤 | 水 | 召唤物与敌人阵营形状区分 |
| 毛笔 | line_delayed | 特殊 | 木 + 毒 | 延迟墨线、双属性、地面预警 |

这 6 件法宝覆盖 6 种攻击模板，并通过双属性覆盖金、木、水、火、土、雷、毒 7 种属性。

**战斗场景：暮春试炼坪**

- 青灰夯土/石坪，外围淡墨山影；中心 65% 保持无高对比装饰。
- 只放低矮石、枯枝、符桩三类装饰；不可碰撞装饰 alpha ≤ 0.55。
- 敌人出生边界用稀疏朱色界桩暗示，不画持续发光边框。

**战斗 HUD：**

- 左上：头像印章 + 生命条 + 护盾细条 + 灵石；生命低于 30% 时增加缺口/心跳图标，不只变红。
- 上中：房间倒计时为最大数字；波次次级；Boss 出现时替换为 Boss 条。
- 右上：只显示“当前生效/差 1 达成”的最多 4 个羁绊徽记；按住详情键展开完整清单。
- 下中：6 格法宝栏，只显示轮廓、星级和冷却扫掠；悬停/聚焦后显示 Tooltip。
- 世界层：敌方危险预警永远使用“朱红 + 三角/斜纹”，玩家火属性仍使用“橙朱 + 火苗符号”，避免颜色单独承担阵营。

**商店：**

- 顶栏固定为“灵石 / 境界修为 / 刷新 / 聚灵 / 下一战”，突破在修为条满时成为主 CTA。
- 主区为 4–5 张商品卡；每张卡优先级：轮廓 icon → 名称/星级 → 体系印 → 属性印 → 攻击形态 → 羁绊预测 → 价格。
- 商品卡新增三种决策条：`可升星`、`购买后激活 X`、`灵石不足`。
- 下区出战栏使用大槽位；储物袋缩小但仍保证 48×48 交互范围；出售区在拖动时才高亮。
- 右栏只展示相关羁绊：当前已拥有、商品能推动、已激活；完整百科进入二级详情。

**Tooltip：**

- 300 ms hover/focus 延迟；靠近卡片但不得覆盖选中卡和价格。
- 第一层：名称、星级、体系/属性、攻击形态、核心一句话、伤害/冷却。
- 第二层：特殊机制、升星差异、当前构筑影响。
- 数值变化使用 `当前 → 购买/升星后`；正负由箭头/符号 + 色彩共同表示。

## 9. 建议实施顺序与验收

1. 固定 1280×720 逻辑 viewport、Canvas Items stretch、keep aspect，并建立 5% safe area。
2. 建立 Theme 和视觉 token，先修字号、焦点、按钮状态、Tooltip 延迟。
3. 完成 6 件法宝 core silhouette，再同时制作 icon 与 world 表现；不得先画卡面插画。
4. 完成玩家与三敌人的灰阶轮廓测试；通过后再上属性/阵营色。
5. 完成战斗场景灰阶版，在 30/50/80 敌人条件下录屏检查。
6. 完成商店信息层级与控制器路径，再加入纸、墨、印章装饰。
7. 在 1280×720、1920×1080、2560×1440、3840×2160、2560×1080、3440×1440 测试。
8. 通过真实试玩后，再批量扩展剩余 27 件法宝、敌人和页面。

验收阈值：

- 所有正文在 1280×720 逻辑分辨率下 ≥ 14 px；关键 HUD ≥ 20 px。
- 所有交互热区 ≥ 48×48；锁定等小图标可以 24 px，但热区不能缩小。
- HUD 静态文字与交互全部位于 90% title-safe；安全区支持 0–10% 设置。
- 所有动态背景文字有 1–2 px 对比描边、阴影或实色底板。
- 任一菜单仅用手柄可进入、操作、退出；Focus Ring 不只改变颜色。
- 减少动态开启时关闭 UI 滑动/弹跳、镜头震动和非必要旋转。
- 伤害数字同一区域同一时间最多显示 5–6 组，连续伤害需要聚合。
